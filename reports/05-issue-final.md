**Title:** A short DB/Redis stall under load starts a self-sustaining socket reconnect loop that exhausts the DB pool; a mass session revoke starts a second 401 loop (reproduced on v0.13.3 and dev, fix verified)

## Summary

After any short backend hiccup (we saw it after a Redis OOM, after a Redis pod recreation, and it reproduces with a
45 s PostgreSQL pause) every open browser tab ends up in a reconnect loop that keeps the database pool saturated
indefinitely: `QueuePool limit ... reached, connection timed out` at hundreds per second, UI down for everyone
(~2.5M pool timeouts in one incident, ~5.8k users). The deployment does not recover after the backend is healthy
again. Revoking all sessions stops that loop but starts a second one: tabs holding revoked tokens loop on
`GET /api/v1/chats/`, `/chats/pinned`, `/folders/` -> 401 for days.

## Analysis (line numbers for v0.13.3; same code on v0.12.5 and dev)

Loop 1 (valid tokens):
1. `socket/main.py` L620 `connect` and L463 `periodic_socket_authentication` (every 30 s, every local socket) verify
   the token via `get_verified_user_by_token` -> `utils/auth.py` L276 `is_valid_token` -> `get_auth()` (DB).
   "Database failures fail closed": a pool timeout counts as an invalid token.
2. L478-485 `get_socket_session_user`: `except Exception:` -> `sio.disconnect(sid)`.
3. `src/routes/+layout.svelte` L293: on `io server disconnect` the client calls `_socket.connect()` with no delay.
4. `src/lib/components/layout/Sidebar.svelte` L864: every `connect` runs `refreshChatRows` (chat list, pinned,
   folders, folder items). In the data `chats` = 2 x reconnects in every window.
The requests generated by reconnects keep the pool busy, the next token check times out, another disconnect follows.
Observed trace: `connect` -> `get_verified_user_by_token` -> `sqlalchemy.exc.TimeoutError: QueuePool limit ...`.

Loop 2 (revoked tokens): `connect` accepts a socket whose token is invalid, just without a user; the `heartbeat`
handler (L723 on v0.12.5) calls `get_socket_session_user`, finds no user and disconnects; the client reconnects and
re-fetches the sidebar -> 401 x3. The client signs out only if a confirmation `GET /api/v1/auths/` returns exactly 401,
which fails under load, so the tab stays.

Also relevant at scale: each heartbeat costs a JWT decode, 2 DB reads, an `UPDATE user.last_active_at` + commit and
2 blocking Redis calls per socket per 30 s, and each sweep check waits up to `DATABASE_POOL_TIMEOUT` for a connection,
so one sweep over a few hundred sockets can run for hours once the pool is saturated.

Related: #32338 (fixed in 0.12.1 by #32341), #32537 (closed without a linked fix). Both describe the symptom; this
report adds a reliable trigger, the mechanism and a verified fix.

## Fix (reference diff, verified; PR available on request)

Diff against dev `67be4e96`: https://github.com/khibye/ope-webui-version-tests/blob/fix/socket-reconnect-storm-v0.12.5/patches/0001-fix-socket-stop-self-sustaining-reconnect-storms-aft.patch
(3 files, +178/-15; the script `patches/apply_fix.py` applies it to v0.12.5, v0.13.3 and dev).

Server (`socket/main.py`):
- distinguish "could not verify" (SQLAlchemy/Redis/timeout errors, `get_auth()`'s 503) from "invalid token": keep the
  socket on the former and retry on the next sweep; disconnect only on the latter
- `connect`: refuse cleanly (`ConnectionRefusedError('backend_unavailable')` / `'unauthorized'`) instead of tearing
  down the transport or accepting an anonymous socket for an invalid token
- heartbeat: no DB re-verification (the sweep does it), never disconnect anonymous sockets, write `last_active_at`
  at most every 300 s (`HEARTBEAT_LAST_ACTIVE_WRITE_INTERVAL`)
- sweep: jitter, `SOCKET_REAUTH_INTERVAL` env, per-check `SOCKET_REAUTH_CHECK_TIMEOUT` (5 s), yield every 50 sockets,
  warn on overrun
- `user-join`: `{error: 'backend_unavailable', retry: true}` instead of failing silently

Client:
- `+layout.svelte`: exponential backoff with jitter (1-30 s) after `io server disconnect` or a refused handshake; on
  `unauthorized` clear the session and go to the login page; retry `user-join` with backoff; sibling tabs follow a
  sign-out via the `storage` event
- `Sidebar.svelte`: skip reconnect-triggered full refreshes within 15 s

Verified with the same reproduction (patched images built on top of the official ones):

| image | trigger | pool timeouts | reconnects after trigger | 401 in last 2 min | result |
|---|---|---|---|---|---|
| v0.13.3 patched | PostgreSQL paused 45 s | 0 | 0 | - | no loop (server logged 32 x "backend unavailable; keeping the session") |
| dev patched | PostgreSQL paused 45 s | 0 | 0 | - | no loop |
| v0.12.5 patched | revoke all sessions | 0 | 47 (80 s burst, then 0) | 0 | all 16 revoked tabs on the login page |

Runs: https://github.com/khibye/ope-webui-version-tests/actions/runs/43628125107,
https://github.com/khibye/ope-webui-version-tests/actions/runs/43850362548. The patched v0.12.5 image has been running
in our production since 2026-11-16: no reconnect loops, CPU back to normal.

Trade-off to be aware of: while the backend is unreachable, an already-open socket keeps its previously verified user
for up to one sweep interval (<= ~45 s longer than today). HTTP requests are unaffected and still fail closed.
