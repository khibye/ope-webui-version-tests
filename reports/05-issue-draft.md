**Title:** Short DB stall under load starts a self-sustaining socket reconnect loop that exhausts the DB pool (reproduced on v0.13.3 and dev)

**Installation Method:** Kubernetes ([Helm chart / manifests]), image `ghcr.io/open-webui/open-webui:v0.12.5`
**Open WebUI Version:** v0.12.5 in production; reproduced on v0.13.3 (`b0e6098`) and dev (`2547992`)

### Summary
After any short backend hiccup (we have seen it after a Redis OOM, after a Redis pod recreation, and it reproduces
with a 45 s PostgreSQL pause), every connected browser tab ends up in a reconnect loop that keeps the database pool
saturated indefinitely: `QueuePool limit ... reached, connection timed out` at hundreds per second, UI down for all
users. The deployment does not recover after the backend is healthy again. Revoking all active sessions is the only
thing that stopped it (and that produces a secondary 401 loop).

### Reproduction (automated, 20 tabs)
Repo: https://github.com/khibye/ope-webui-version-tests - `docker compose` with PostgreSQL behind toxiproxy, Redis,
`WEBSOCKET_MANAGER=redis`, `DATABASE_POOL_SIZE=2` / overflow 0 / timeout 5 s so that 20 Playwright tabs stand in for
thousands. 90 s clean baseline, +100 ms DB latency (still clean), then **PostgreSQL paused for 45 s**, then 6 min
observation. Run: https://github.com/khibye/ope-webui-version-tests/actions/runs/43204023545

| image | revision | pool timeouts | socket reconnects after trigger | 15 s windows >2 min after trigger with timeouts |
|---|---|---|---|---|
| v0.13.3 | b0e6098 | 347 | 214 | 16 / 16 |
| dev | 2547992 | 602 | 205 | 17 / 17 |

Six minutes after PostgreSQL is back, 20 idle tabs still reconnect ~5 times per 10 s and the pool is still timing out.
Recreating Redis (gone 60 s) did not start the loop at this scale; in production it did (we assume it caused the
first DB stall).

### Analysis (same code on v0.12.5 / v0.13.3 / dev; line numbers for v0.13.3)
1. `backend/open_webui/socket/main.py` L620 `connect`: the socket is accepted only after
   `get_verified_user_by_token` -> `utils/auth.py` L276 `is_valid_token` -> `get_auth()` (DB). "Database failures
   fail closed": a pool timeout = invalid token. Observed trace:
   ```
   File "/app/backend/open_webui/socket/main.py", line 626, in connect
       user = await get_verified_user_by_token(auth['token'], redis)
   sqlalchemy.exc.TimeoutError: QueuePool limit of size 2 overflow 0 reached, connection timed out, timeout 5.00
   ```
2. `socket/main.py` L463 `periodic_socket_authentication`: every 30 s all local sockets are re-verified against the
   DB; L478-485 `get_socket_session_user`: `except Exception:` -> `sio.disconnect(sid)`. Any transient DB error
   disconnects the socket.
3. `src/routes/+layout.svelte` L293: on `io server disconnect` the client calls `_socket.connect()` with no delay.
4. `src/lib/components/layout/Sidebar.svelte` L864: every `connect` runs `refreshChatRows` (chat list, pinned,
   folders, folder items) - several DB-backed requests per reconnect. In the data `chats` = 2 x reconnects in
   every window.

The requests generated by reconnects keep the pool busy, so the next connect's token check times out, which causes
another reconnect. The load is a product of the loop itself, so removing the trigger does not end it.

Secondary: a tab whose token was revoked signs out only if `GET /api/v1/auths/` succeeds; under load it fails and the
tab keeps looping with 401s (each still a DB lookup).

Related: #32338 (fixed in 0.12.1 by #32341), #32537 (closed without a linked fix). Both describe the symptom; this
report adds a reliable trigger and the mechanism.

### Suggested fixes
- Treat "could not verify" (DB/Redis error) differently from "invalid token" in the connect handler and in the
  periodic re-verification: keep the socket, retry later.
- Jittered exponential backoff before reconnecting after `io server disconnect`.
- Do not refresh the full sidebar on every reconnect (or debounce it).
- Spread/cached periodic re-verification so the DB is not a single point of failure for the realtime layer.
- Client: retry the sign-out confirmation with backoff instead of looping on 401.
